## Contribution

### 1. Code Style セクションのカバー範囲について

リードのドラフト（`team-practices.md` 119–125行目）は「サブコマンドハンドラの命名は
コマンド名を接頭辞にする（`run_scan`/`run_clean`/`run_audit`）」という**命名の1点**は
提起しているが、実際のコードを確認したところ、命名だけでは解決しない**モジュール境界**の
論点が少なくとも3つ未整理のまま残っており、Code Style セクションはこの点で不十分と判断する。

- **既存の `CliApp` メソッド命名と衝突しうる層の違いが明示されていない。**
  現行 `src/cli.rs` の `CliApp` は `scan_all` / `select` / `plan` / `confirm` / `execute` /
  `render_output` / `scan_fully_failed` という、`run_`接頭辞を持たないドメイン動詞命名で
  メソッドを持つ。ここに新たに `run_scan`/`run_clean`/`run_audit` という「コマンド分岐の
  ハンドラ」を導入する場合、それが (a) `CliApp` 自身のメソッドとして追加されるのか、
  (b) `main.rs` 側（現状の `to_sdk_credentials`/`action_kind_from_prompt` などと同じ
  「バイナリ側の合成・配線層」）の自由関数として追加されるのか、(c) 新設モジュール
  （例: `src/commands/` や `cli.rs` 内の別ブロック）に置かれるのかで、既存の命名慣習との
  整合性が変わる。`CliApp::scan_all` と `run_scan` が同一ファイル内に並ぶと、どちらが
  「ドメインロジック」でどちらが「CLI分岐ハンドラ」かが名前だけでは読み取れず、
  `architecture.md` が明言する ports-and-adapters の層区分（ライブラリ＝ドメイン、
  `main.rs`＝アダプタ配線）を命名でも可視化する必要がある。ドラフトはこの「どの層に
  置くか」を Code Style として確定しておらず、`evidence.md` 65行目の未解決事項3も
  命名パターンの是非のみを問うており、配置先モジュールの是非を問うていない。
- **`audit` 閲覧サブコマンドの読み取りAPIをどのモジュールに置くか未定。**
  `architecture.md`（184–186行目）は「`AuditLogger`/`AuditWrite` は追記専用であり、
  `audit` 閲覧サブコマンドには読み取りAPIの追加が必要」と明記している。この新規
  読み取りAPI（例: `AuditRead` trait）を既存の `src/audit.rs`（1モジュール1コンポーネント
  という `code-structure.md` の原則を踏襲するなら自然）に追加するのか、独立した
  新モジュールに切り出すのかは、Code Style/モジュール構成の判断であり、命名規則
  だけでは決まらない。ドラフトはこの点に触れていない。
- **共通フラグ（`--role-name` 等）の配分方法が Code Style 上未確定のまま。**
  `evidence.md`（66–69行目）の未解決事項4で既にこの論点自体は認識されているが、
  `team-practices.md` の Code Style セクション（119–125行目）はハンドラ命名のみを
  追記し、`#[command(flatten)]` を使うか各サブコマンドで重複定義するかという
  「`Cli`/`Commands` 構造そのものの設計方針」は Code Style として言及していない。
  これは単なる実装詳細ではなく、`src/cli.rs` の型構造（モジュール内の構造体設計）を
  左右するため、Code Style セクションの守備範囲に含めるべきか、少なくとも
  「本セクションでは扱わない／Code Generation 段階の設計判断とする」という判断を
  明記すべきである。

### 2. `run_scan`/`run_clean`/`run_audit` 命名の既存慣習との整合性評価

部分的に整合するが、無条件に既存慣習の延長とは言えない。

- 既存コードで唯一「動詞のみ・接頭辞なし」の命名パターン（`scan_all`, `execute`,
  `verify`, `plan`）を踏襲するなら、ハンドラは `run_` を付けずに `scan`/`clean`/`audit`
  という短い名前だけで十分表現できる可能性がある（`clap::Subcommand` の各バリアント名
  `Scan`/`Clean`/`Audit` と対応する分だけで、関数名が指す対象は自明）。`run_` 接頭辞は
  「Rust CLI 実装で一般的なパターン」ではあるが、**このコードベース固有の慣習**ではなく、
  team.md の既存 Code Style（「ドメイン語彙は型名・関数名で一貫させ、略語を避ける」
  「スキャン時点の Identity 検証と削除直前の二重 Identity 検証は役割が名前から読み取れる
  よう別関数として命名を分離する」）から演繹される規則でもない。むしろ既存の慣習が
  求めているのは「同じ動詞（`verify`）を役割ごとに別名にする」ことであり、これは
  「コマンド名を接頭辞にする」設計思想とは方向性が異なる（接頭辞方式は「同じ動詞に
  異なる主語を付ける」発想に近い）。
- 加えて、`src/identity.rs` の実装（`cli.rs`/`main.rs` から見える限り）では、スキャン時と
  実行直前の Identity 検証はいずれも `IdentityCheck::verify` という**単一の trait メソッド**
  経由で呼ばれており、呼び出し箇所のコメントで役割を区別しているだけで、team.md が
  affirm 済みの「別関数として命名を分離する」方針が実装上どこまで徹底されているかは
  今回読んだ範囲（`cli.rs`/`main.rs`）では確認できなかった。もしこの既存の命名分離方針が
  実際には未達成であれば、新規の `run_scan`/`run_clean`/`run_audit` 命名パターンだけを
  厳格に運用しても、既存の不整合を追認するだけになりかねない。人間インタビューで
  「命名分離方針は `identity.rs` 内でどう実装されているか」を確認し、新規パターンとの
  整合性を取ることを推奨する。

### 3. エラーハンドリング・モジュール構成に関してインタビューで解決すべき点

- **`audit` サブコマンドの異常系ハンドリング方針が未定。** 監査ログ（JSON Lines）の
  読み取り時、不正フォーマットや欠落フィールドを持つ行に遭遇した場合、(a) 即座にエラーで
  中断する（既存の「本番コードパスで `unwrap`/`expect`/`panic!` 禁止、エラーは `Result` で
  伝播」という Forbidden 方針とは別軸で、"1行でも壊れていれば全体を失敗とするか"）、
  (b) 当該行をスキップし警告ログを出して継続するか、という選択肢がある。これは
  `scan_all` の「1アカウント×1リージョンの失敗は他を止めない」というバルクヘッド
  分離方針（`architecture.md` Key Design Decisions）と平仄を合わせるべきかどうかも含め、
  team-practices.md のドラフト（79–80行目）は「異常系テストを要求する」とは書いているが、
  失敗時の継続/中断方針そのものには触れていない。テスト要件を書く前に、まず挙動方針を
  インタビューで確定すべきである。
- **`run_audit` の読み取り専用制約を型システムで構造的に担保するか。**
  `discovered-rules.md`（34–37行目）の追加候補は「`audit` は読み取り専用の経路とする」
  制約を project.md へ昇格すべきか team.md 相当に留めるべきかを問うているが、これは
  モジュール境界の設計判断（`run_audit` ハンドラに `ActionApiOperations`/`AuditWrite` への
  参照を一切渡さず、`AuditRead` のような読み取り専用traitのみを注入する構造にすれば、
  実装ミスでの誤操作が型レベルで不可能になる）と直結する。Code Style/モジュール設計の
  観点から、「`scan`/`clean`/`audit` それぞれのハンドラに注入する依存（trait オブジェクト）
  の集合を分離する」という構造的な担保方針を Code Style セクションに明記すべきかを
  インタビューで確認したい。
- **サブコマンドごとの `Result` 型／終了コード契約の継承関係が未確認。**
  現行 `main()` は `Result<(), Box<dyn std::error::Error>>` を返し、`CliApp::scan_fully_failed`
  による終了コード判定（README.md記載のCI向け契約、R-03）を持つ。サブコマンド化後、
  `scan`/`clean`/`audit` それぞれが独自の終了コード契約を持ちうるか（特に `audit` は
  スキャン失敗という概念がそもそも存在しないため、既存の「全滅判定」ロジックが
  流用できない）を確認する必要がある。これは Testing Posture 側でも言及がなく、
  Code Style（エラー型・終了コードの一貫した設計方針）としても未整理。

## Positions

- OBJECT: Code Style セクション（`team-practices.md` 119–125行目）はハンドラ命名のみを
  扱っており、命名の前提となる「どの層・どのモジュールに配置するか」を確定していない
  ため、モジュール境界の設計判断（`CliApp` 内 vs `main.rs` 側 vs 新設モジュール）を
  インタビューで確認し、Code Style に明記する必要がある。
- OBJECT: `run_scan`/`run_clean`/`run_audit` という接頭辞方式は、既存コードベースが
  実際に採用している「動詞のみ・役割ごとに別名にする」命名慣習（`scan_all`/`execute`/
  `verify` 等）の自然な延長とは言い切れず、一般的な Rust CLI 慣習からの新規導入である
  ことを明示した上で affirm すべきである。
- OBJECT: `audit` サブコマンドの異常系（監査ログの不正フォーマット行）に対する
  継続/中断方針が Testing Posture・Code Style のいずれにも明記されておらず、
  テスト要件（79–80行目）を固定する前に挙動方針自体をインタビューで確認すべきである。
- AGREE: `scan`/`clean`/`audit` という3サブコマンド構成、および `clean` のみが M6ゲート・
  破壊的操作の担い手であるという分類（Walking Skeleton セクション 34–37行目）は、
  実コード（`architecture.md`のサブコマンド化設計要点、`cli.rs`の `--scan-only`/`--execute`
  相互排他フラグ）と整合しており妥当と判断する。
