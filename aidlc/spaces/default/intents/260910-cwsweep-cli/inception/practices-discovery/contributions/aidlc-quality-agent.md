## Contribution

QAの観点から、リードのドラフト（`team-practices.md`／`discovered-rules.md`）とスコープ文書を突き合わせて評価する。本ツールの中核リスクは「Organization横断で `delete-log-group` / `put-retention-policy` という不可逆・破壊的なAPIを、単一開発者体制で、複数人レビューという安全網なしに実行する」点にある。したがってテスト戦略の妥当性判断基準は、機能カバレッジではなく **安全制御（dry-run既定、二重Identity検証、全選択禁止、監査ログ必須）が「実装として存在する」ことと「壊れたら必ず検出される」ことの両方をテストが保証しているか** に置く。

### 評価できる点

- Testing Postureのドラフトが、80%行カバレッジのfloorとは別に、安全クリティカルパス（Identity検証失敗系、`--execute`未指定時の抑止、マルチセレクト初期状態）について100%パスカバレッジ＋境界値テストを追加要件として提案している点は妥当。これは「平均的なカバレッジ率」では破壊的操作の安全性を測れないという認識が正しく反映されている。
- test-after／層ごとの実装直後テストという方針自体は、単一開発者・スコープが明確なCLIには過剰でなく現実的。
- CIでの`cargo fmt --check`／`cargo clippy -D warnings`実行は最低限のゲートとして妥当。

### 不十分・要補強と考える点（インタビューで確定させたい）

1. **テストの「種類」がユニットテストに閉じている。** スコープ文書のMandated/Forbidden項目（例: `sts:get-caller-identity`不一致時の即失敗、削除直前の二重Identity検証、ページネーション全件取得、AssumeRoleの使い分け）は、AWS SDKとのI/O境界にまたがるロジックであり、モック化したAWS SDKクライアントに対する**統合テスト相当のテスト**（少なくともAWS SDK for Rustのテストダブル／`aws-smithy`のモックレスポンスを使ったシナリオテスト）がなければ「ユニットテストで関数を単体で叩いて緑」というだけで安全性の検証にならない。ドラフトには単体テストという言葉しかなく、境界を跨ぐシナリオテスト（例: 1account分のスキャン→選択→削除の一連の流れをモックAWS環境で再現）の位置づけが明記されていない。
2. **「テストが安全制御を破壊から守れているか」を検証する仕組み（変異テスト・退行テスト）の言及がない。** 例えば「dry-runが既定」という制御は、将来のリファクタでフラグのデフォルト値が誤って反転しても、対応するテストが「デフォルト値を明示的に上書きしてから検証」していれば検出できない。この種のリグレッションを防ぐには、少なくとも「フラグを一切指定しない状態での呼び出し」を必須テストケースとして固定化する規約が要る。ドラフトの「境界値テスト」がここまで踏み込むかは未確定。
3. **本物のAWS環境に対する動作確認（統合検証）の位置づけが曖昧。** Deploymentの節でM6リリースタグに「実Organization環境での動作確認済みチェックリスト」を求めている点は良いが、これは手動チェックリストであり自動テストではない。単一開発者体制で人手のチェックリストだけに頼ると、チェック項目の形骸化リスクがある。せめてサンドボックス的な検証用AWSアカウント（本番Organizationではなく個人のテストアカウント）に対する**最小限の実環境スモークテスト**（dry-runでの一覧取得のみ、実削除は含まない）をCIまたはリリース前の定型手順として持つべきか、インタビューで確認したい。
4. **監査ログのテストが明示されていない。** 監査ログは「無効化オプションを設けない」という必須要件であり、削除操作の事後追跡可能性を支える唯一の記録である。ログ出力の欠落・フォーマット崩れ・失敗時ログ未記録は本ツールにとって重大な欠陥だが、ドラフトのテスト方針には監査ログの出力内容・失敗系での記録有無を検証するテストへの言及がない。
5. **CI上でAWS認証情報を必要とするテストの扱いが未定義。** モックで完結するテスト（大多数）とAWS実アカウントに接触するテスト（統合/スモーク）を分離する方針、CIでは前者のみ実行し後者は手動実行に限定するのか、が決まっていない。誤って実AWS呼び出しを行うテストがCIで自動実行される事故を防ぐため、明示的な分離規約が必要。
6. **カバレッジ計測ツールの指定がない。** Rustプロジェクトとして `cargo llvm-cov` または `cargo tarpaulin` のどちらを採用しCI上で80%floorをどう強制するか（PRブロックの仕組み）が未確定。
7. **`clippy`の警告レベルについて**、安全クリティカルなツールである以上、`-D warnings` を緩めない（allowの例外を作らない）ことを推奨する。特に`unwrap()`/`expect()`の多用はAWS API呼び出し境界での予期しないパニックにつながるため、`clippy::unwrap_used` 系のlintを安全パス（Identity検証、削除実行）だけでも有効化することを提案したい。

### 結論

現行ドラフトのテスト戦略は「量」（80%floor、100%安全パスカバレッジ）については妥当な水準を提案できているが、「質」（統合テスト/シナリオテストの位置づけ、退行防止のためのデフォルト値検証、監査ログ検証、実環境検証の扱い）についてはインタビューでの確定が必要と考える。
